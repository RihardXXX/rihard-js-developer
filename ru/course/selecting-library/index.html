26 Как выбрать библиотеку для ФП

Цель урока Научиться выбирать между Vanilla JS, Lodash, Ramda, Sanctuary, fp-ts и Effect по критериям проекта и команды — бюджету, этапу, команде, качеству, производительности и парадигме, — а не по вкусу и моде.

Когда перед вами стоит выбор, что выбрать из библиотек, описанных в курсе и ниже, или ванильного решения, не стоит опираться на следующие принципы, которые я часто встречал в своей практике при коммерческой разработке. Не стоит придерживаться следующего:

  1. Мне нравится эта библиотека (хотелки).
  2. Это сейчас модно (хотелки).
  3. Я главный, я решаю и я так хочу (хотелки).

Все выше описанное это не профессиональный подход.

На что следует обратить внимание. Какие критерии важны при выборе:

  1. Бюджет. Очень важно понять платежеспособность инвестора (клиента) и его планы на будущее. Это очень важный пункт и можно сказать один из основных.
  2. Насколько % проект завершён или он находится в начале. Аналогично: если проект написан и все работает корректно, не нужно его переписывать.
  3. Кто работает с тобой в команде и сколько вас человек. Нужно понимать процесс онбординга нового разработчика в команду, знаком ли он с данной библиотекой и твоими архитектурными решениями.
  4. Качество продукта. Чем выше сложность, тем зачастую качество будет расти.
  5. Перфоманс. Это не самый важный фактор, так как зачастую ошибка в логике приложения даст просадку, а не какая-либо библиотека.
  6. Парадигма функционального программирования.

Vanilla JS

  1. Бюджет. Бюджет небольшой или средний.
  2. Насколько % проект завершён или он находится в начале. Когда проект уже ранее был начат на JS и вышел за горизонт и финишную прямую.
  3. Кто работает с тобой в команде и сколько вас человек. Для малых команд с глубокими знаниями JS. Порой такая команда работает эффективнее большой, где язык знают поверхностно. Глубокое знание JS нужно и в проектах на TypeScript: типы проверяются при компиляции и сами по себе не защищают от ошибок в данных, которые приходят во время выполнения.
  4. Качество продукта. Зависит от команды, сроков и бюджета, зачастую невысокое.
  5. Перфоманс. Будет самый высокий при аналогичном коде относительно библиотек.
  6. Парадигма функционального программирования. Полная свобода: процедурный, ООП, ФП и т.п. И каждый как хочет.

Lodash

  1. Бюджет. Подходит для проектов любого масштаба, но лучше использовать на средних проектах.
  2. Насколько % проект завершён или он находится в начале. Только если проект не достиг горизонта, а находится на начальном этапе.
  3. Кто работает с тобой в команде и сколько вас человек. Для команд любого размера, поверхностно знакомых с функциональным программированием, которые хотят упростить рутину.
  4. Качество продукта. Зависит от команды, сроков и бюджета, зачастую невысокое.
  5. Перфоманс. Будет ниже ванилы при аналогичном коде. Бандл библиотеки оптимизирован по размеру.
  6. Парадигма функционального программирования. Не совсем функциональна: проблемы с иммутабельностью и передачей аргументов в композиции функций, когда на первом месте функции принимают данные, а потом уже функцию. Эти проблемы снимает модуль lodash/fp: в нем функции каррированы, не мутируют данные и принимают их последним аргументом. Для тех, кто только трогает функциональное программирование.

Ramda

  1. Бюджет. Подходит для проектов любого масштаба.
  2. Насколько % проект завершён или он находится в начале. На любом этапе, кроме ситуаций, когда проект уже завершается или уже присутствует другая библиотека для работы с данными.
  3. Кто работает с тобой в команде и сколько вас человек. Для команд любого размера, поверхностно или профессионально использующих функциональное программирование, которые хотят упростить рутину.
  4. Качество продукта. Качество продукта, как правило, высокое.
  5. Перфоманс. Будет ниже ванилы при аналогичном коде. Бандл библиотеки необходимо оптимизировать, если планируется использование только небольшой части 5-10% функций.
  6. Парадигма функционального программирования. Используется полноценное функциональное программирование. Покрывает до 98% кейсов при работе с данными и подойдет для всех проектов. Своя философия в рамках функционального программирования. Проще для новичков в функциональном программировании и задает правильный тон. Нет болячек Lodash.

Sanctuary

  1. Бюджет. Подходит для масштабных проектов с бюджетом выше среднего.
  2. Насколько % проект завершён или он находится в начале. Желательно использовать на начальном этапе.
  3. Кто работает с тобой в команде и сколько вас человек. Для команд любого размера, профессионально использующих функциональное программирование и понимающих, что они пишут.
  4. Качество продукта. Качество продукта, как правило, высокое.
  5. Перфоманс. Будет ниже ванилы при аналогичном коде.
  6. Парадигма функционального программирования. Используется полноценное функциональное программирование со своей философией, которая строже придерживается принципов ФП. Полноценное использование монад и прочих абстрактных типов. Высокий порог входа. Для тех, кто действительно в теме функционального программирования. Своя архитектура мышления. Учтите, что последний релиз Sanctuary, 3.1.0, вышел 9 августа 2020 года (по данным реестра npm на октябрь 2026 года).

Следующие две библиотеки рассчитаны на TypeScript. Из JavaScript их тоже можно вызывать, но основную пользу они дают вместе с проверкой типов: отсутствие значения и возможные ошибки видны в типах, и компилятор проверяет, как код с ними обращается.

fp-ts

  1. Бюджет. Подходит для проектов среднего и крупного масштаба с бюджетом не ниже среднего: команде нужно время на обучение.
  2. Насколько % проект завершён или он находится в начале. Прежде всего для проектов, где fp-ts уже используется. Новым пользователям README fp-ts предлагает смотреть на Effect как на преемника fp-ts v2.
  3. Кто работает с тобой в команде и сколько вас человек. Для команд любого размера, которые пишут на TypeScript и профессионально используют функциональное программирование: нужно понимать Option, Either, Task и классы типов, например функтор и монаду.
  4. Качество продукта. Качество продукта, как правило, высокое: отсутствие значения и ошибки видны в типах Option и Either, и компилятор напоминает обработать оба случая.
  5. Перфоманс. Будет ниже ванилы при аналогичном коде: значения заворачиваются в Option и Either, а шаги pipe — это дополнительные вызовы функций. Модули подключаются по отдельности (fp-ts/Option, fp-ts/Either), всю библиотеку тянуть не нужно.
  6. Парадигма функционального программирования. Полноценное и строгое типизированное функциональное программирование по образцу Haskell, PureScript и Scala: классы типов и эмуляция типов высших родов (higher-kinded types), которые TypeScript сам не поддерживает. Высокий порог входа. Проект fp-ts объявил о слиянии с экосистемой Effect, а его автор, Джулио Канти, присоединился к организации Effect. Учтите, что последний релиз fp-ts, 2.16.11, вышел 18 августа 2025 года (по данным реестра npm на октябрь 2026 года).

Effect

  1. Бюджет. Подходит для проектов среднего и крупного масштаба, где цена ошибки высока и есть время на обучение команды.
  2. Насколько % проект завершён или он находится в начале. Лучше всего на начальном этапе. В готовый проект Effect можно вводить постепенно: Effect.runPromise возвращает обычный Promise, поэтому новый код уживается со старым.
  3. Кто работает с тобой в команде и сколько вас человек. Для команд любого размера, которые пишут на TypeScript и готовы освоить новую модель: тип Effect<A, E, R>, генераторы Effect.gen, сервисы и слои (Layer). Теорию категорий знать не обязательно: код в Effect.gen читается последовательно, почти как async/await.
  4. Качество продукта. Качество продукта, как правило, высокое: возможные ошибки и нужные зависимости видны в типе Effect<A, E, R>, а повторы, тайм-ауты, отмена и конкурентность встроены в библиотеку.
  5. Перфоманс. Будет ниже ванилы при аналогичном коде: программы выполняет собственный рантайм Effect на файберах. Неиспользуемые модули отсекаются при сборке (tree shaking), а в версии 4 рантайм переписан, чтобы расходовать меньше памяти и работать быстрее.
  6. Парадигма функционального программирования. Полноценное и строгое типизированное функциональное программирование, нацеленное на продакшен. Эффекты — это значения: Effect только описывает работу и ничего не делает, пока его не запустит рантайм, а возможные ошибки и нужные зависимости записаны в типе Effect<A, E, R>. Кроме того, в библиотеку входят конкурентность на файберах и Schema для проверки данных во время выполнения. Высокий порог входа, но другого рода, чем у fp-ts: осваивать нужно не классы типов, а модель эффектов и большой API. По README fp-ts, Effect можно считать преемником fp-ts v2. Текущая мажорная версия — 4: Effect 4.0.0 вышел 1 октября 2026 года, а ветка 3.x ещё получает исправления (по данным реестра npm на октябрь 2026 года).

Можно себе представить приверженность к функциональному программированию.

Vanilla JS (присутствует) -> Lodash (не полноценное) -> Ramda (полноценное) -> Sanctuary (полноценное и строгое)

В TypeScript рядом с ними стоят fp-ts (полноценное и строгое, на классах типов) и Effect (полноценное и строгое, с эффектами и ошибками в типах).

Главное

  • Выбирать библиотеку по принципам «мне нравится», «это модно» и «я главный, я так хочу» — непрофессиональный подход.
  • Критерии выбора: бюджет, этап проекта, команда и онбординг новых разработчиков, качество продукта, производительность и парадигма функционального программирования.
  • Производительность — не самый важный фактор: просадку чаще даёт ошибка в логике приложения, а не библиотека.
  • Lodash не совсем функциональна: есть проблемы с иммутабельностью, а функции принимают сначала данные и только потом функцию, что мешает композиции. Эти проблемы снимает модуль lodash/fp: в нём функции каррированы, не мутируют данные и принимают их последним аргументом.
  • По приверженности к функциональному программированию варианты выстраиваются так: Vanilla JS (присутствует) -> Lodash (не полноценное) -> Ramda (полноценное) -> Sanctuary (полноценное и строгое). В TypeScript к ним добавляются fp-ts и Effect, а README fp-ts предлагает считать Effect преемником fp-ts v2.

Упражнения

Упражнение 1

Из списка заказов получите строку с названиями оплаченных заказов дороже 100 — через запятую, в алфавитном порядке. Решите задачу трижды: на Vanilla JS методами массива, на Ramda (R.pipe, R.filter, R.map и другие) и на Sanctuary (S.pipe со списком функций, S.filter, S.map, S.prop, S.sort, S.joinWith). Сравните, как в каждом варианте передаются данные и как собирается композиция.

Заготовка

const orders = [
  { title: 'keyboard', total: 120, paid: true },
  { title: 'mouse', total: 40, paid: true },
  { title: 'monitor', total: 300, paid: false },
  { title: 'laptop', total: 900, paid: true },
  { title: 'cable', total: 15, paid: false },
]

// ваш код: withVanilla, withRamda и withSanctuary :: [Object] -> String

console.log(`Vanilla JS: ${withVanilla(orders)}`)
console.log(`Ramda: ${withRamda(orders)}`)
console.log(`Sanctuary: ${withSanctuary(orders)}`)

Ожидаемый вывод

Vanilla JS: keyboard, laptop
Ramda: keyboard, laptop
Sanctuary: keyboard, laptop
Показать решение
const orders = [
  { title: 'keyboard', total: 120, paid: true },
  { title: 'mouse', total: 40, paid: true },
  { title: 'monitor', total: 300, paid: false },
  { title: 'laptop', total: 900, paid: true },
  { title: 'cable', total: 15, paid: false },
]

// Vanilla JS: цепочка методов, данные — сам массив
// withVanilla :: [Object] -> String
const withVanilla = (list) =>
  list
    .filter((order) => order.paid && order.total > 100)
    .map((order) => order.title)
    .sort()
    .join(', ')

// Ramda: функции каррированы и принимают данные последним аргументом
// withRamda :: [Object] -> String
const withRamda = R.pipe(
  R.filter(R.prop('paid')),
  R.filter(R.pipe(R.prop('total'), R.lt(100))), // R.lt(100)(total) — это 100 < total
  R.map(R.prop('title')),
  R.sortBy(R.identity),
  R.join(', '),
)

// Sanctuary: S.pipe принимает массив функций, данные тоже идут последним аргументом
// withSanctuary :: [Object] -> String
const withSanctuary = S.pipe([
  S.filter(S.prop('paid')),
  S.filter(S.pipe([S.prop('total'), S.gt(100)])), // S.gt(100)(total) — это total > 100
  S.map(S.prop('title')),
  S.sort,
  S.joinWith(', '),
])

console.log(`Vanilla JS: ${withVanilla(orders)}`)
console.log(`Ramda: ${withRamda(orders)}`)
console.log(`Sanctuary: ${withSanctuary(orders)}`)

Упражнение 2

Найдите название первого оплаченного заказа дороже заданной суммы, а если такого нет, верните «нет». Сделайте это на Ramda через R.find и на Sanctuary через S.find, S.map и S.fromMaybe, проверьте на суммах 500 и 1000. Затем выведите, что возвращают сами R.find и S.find, когда подходящего заказа нет. Чем ответ Sanctuary надёжнее?

Заготовка

const orders = [
  { title: 'keyboard', total: 120, paid: true },
  { title: 'mouse', total: 40, paid: true },
  { title: 'monitor', total: 300, paid: false },
  { title: 'laptop', total: 900, paid: true },
  { title: 'cable', total: 15, paid: false },
]

// isPaidOver :: Number -> Object -> Boolean
const isPaidOver = (limit) => (order) => order.paid && order.total > limit

// ваш код: titleWithRamda и titleWithSanctuary :: Number -> [Object] -> String

console.log(`Ramda, 500: ${titleWithRamda(500)(orders)}`)
console.log(`Ramda, 1000: ${titleWithRamda(1000)(orders)}`)
console.log(`Sanctuary, 500: ${titleWithSanctuary(500)(orders)}`)
console.log(`Sanctuary, 1000: ${titleWithSanctuary(1000)(orders)}`)

Ожидаемый вывод

Ramda, 500: laptop
Ramda, 1000: нет
Sanctuary, 500: laptop
Sanctuary, 1000: нет
undefined
Nothing
Показать решение
const orders = [
  { title: 'keyboard', total: 120, paid: true },
  { title: 'mouse', total: 40, paid: true },
  { title: 'monitor', total: 300, paid: false },
  { title: 'laptop', total: 900, paid: true },
  { title: 'cable', total: 15, paid: false },
]

// isPaidOver :: Number -> Object -> Boolean
const isPaidOver = (limit) => (order) => order.paid && order.total > limit

// Ramda: R.find возвращает заказ или undefined, пустоту проверяем сами
// titleWithRamda :: Number -> [Object] -> String
const titleWithRamda = (limit) => R.pipe(
  R.find(isPaidOver(limit)),
  (order) => (order === undefined ? 'нет' : order.title),
)

// Sanctuary: S.find возвращает Maybe — Just (заказ) или Nothing,
// S.map и S.fromMaybe обрабатывают оба случая
// titleWithSanctuary :: Number -> [Object] -> String
const titleWithSanctuary = (limit) => S.pipe([
  S.find(isPaidOver(limit)),
  S.map(S.prop('title')),
  S.fromMaybe('нет'),
])

console.log(`Ramda, 500: ${titleWithRamda(500)(orders)}`)
console.log(`Ramda, 1000: ${titleWithRamda(1000)(orders)}`)
console.log(`Sanctuary, 500: ${titleWithSanctuary(500)(orders)}`)
console.log(`Sanctuary, 1000: ${titleWithSanctuary(1000)(orders)}`)

// заказа дороже 1000 нет: Ramda возвращает undefined, Sanctuary — Nothing
console.log(R.find(isPaidOver(1000))(orders))
console.log(S.find(isPaidOver(1000))(orders))

// undefined легко пропустить: забытая проверка уронит код дальше,
// например на чтении order.title. Maybe прямо говорит, что результата
// может не быть, и S.map и S.fromMaybe обрабатывают оба случая
