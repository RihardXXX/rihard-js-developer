25 ФП в TypeScript и Effect

Цель урока Увидеть, как идеи курса — композиция через pipe, Maybe и Either, эффекты как значения — выглядят в TypeScript на Effect 4, научиться читать тип Effect<A, E, R> и решать, когда переход на Effect окупается.

Этот урок — мост от курса к продакшен-коду. Сквозной пример из урока «Функциональное программирование» — взять пользователей онлайн старше 20 лет и получить имя первого — здесь переписан на TypeScript с библиотекой Effect 4. Задача та же, и ответ тот же — John, а по шагам видно, что добавляет каждый слой: типы, Option вместо Maybe, проверку входящих данных и ошибки в типе программы.

Курс написан на JavaScript, потому что идеи функционального программирования не зависят от системы типов, а на JS они видны без лишнего синтаксиса. В продакшене их часто пишут на TypeScript: там отсутствие значения и возможные ошибки становятся частью сигнатуры, и их обработку проверяет компилятор. Примеры на TypeScript в этом уроке только для чтения, песочница их не запускает. Оба упражнения в конце урока — на чистом JavaScript, их можно запустить в песочнице, как обычно.

Как читать TypeScript

TypeScript — это JavaScript с аннотациями типов: компилятор их проверяет, а перед запуском стирает. Аннотация пишется через двоеточие: name: string — строка, age: number — число. Union-тип 'online' | 'offline' разрешает только одно из перечисленных значений. Дженерик <A> — параметр типа, та же переменная a из урока «Нотация типов Хиндли–Милнера», только с большой буквы: сигнатура head :: [a] -> Maybe a в TypeScript записывается как <A>(self: ReadonlyArray<A>) => Option<A>. ReadonlyArray — массив, который функция обещает не менять.

TypeScript
import { Option } from 'effect'

// Union-тип: статус может быть только одной из двух строк
type Status = 'online' | 'offline'

// Форма пользователя: имена полей и их типы
interface User {
  readonly name: string
  readonly status: Status
  readonly age: number
}

// Хиндли–Милнер: head :: [a] -> Maybe a
// TypeScript:    <A>(self: ReadonlyArray<A>) => Option<A>
// <A> — параметр типа, та же переменная a, только с большой буквы
// Option.Option<A> — тип Option из модуля Option
const head = <A>(self: ReadonlyArray<A>): Option.Option<A> =>
  self.length > 0 ? Option.some(self[0]) : Option.none()

const users: ReadonlyArray<User> = [
  { name: 'John', status: 'online', age: 25 },
]

console.log(Option.isSome(head(users))) // true
console.log(Option.isNone(head([]))) // true

// head(42) не скомпилируется: число не массив
// { name: 'Bob', status: 'away', age: 30 } тоже: 'away' не входит в Status

pipe и Option вместо S.pipe и Maybe

Теперь чистая часть примера. Функция pipe из effect принимает сначала значение, а затем шаги конвейера: pipe(x, f, g) делает то же, что S.pipe([f, g])(x) в Sanctuary. Если значения ещё нет и нужна сама функция-конвейер, её собирает flow(f, g). Модуль Array из effect даёт filter и head, а head возвращает Option — аналог Maybe: Some со значением или None.

TypeScript
// Array из effect назван Arr, чтобы не закрыть встроенный Array
import { Array as Arr, Option, pipe } from 'effect'

interface User {
  readonly name: string
  readonly status: 'online' | 'offline'
  readonly age: number
}

const users: ReadonlyArray<User> = [
  { name: 'John', status: 'online', age: 25 },
  { name: 'Alex', status: 'offline', age: 18 },
  { name: 'Angel', status: 'online', age: 18 },
]

const isOnline = (user: User): boolean => user.status === 'online'
const olderThan = (age: number) => (user: User): boolean => user.age > age

// searchOnlineUser :: [User] -> String
const searchOnlineUser = (list: ReadonlyArray<User>): string =>
  pipe(
    list, // в pipe из effect первым идёт значение, а не массив функций
    Arr.filter(isOnline), // только пользователи онлайн
    Arr.filter(olderThan(20)), // только старше 20 лет
    Arr.head, // Option<User>: Some(пользователь) или None для пустого списка
    Option.map((user) => user.name), // имя внутри Option
    Option.getOrElse(() => ''), // достаём имя, для None будет ''
  )

console.log(searchOnlineUser(users)) // 'John'
console.log(searchOnlineUser([]) === '') // true

Ответ тот же — John. Одно отличие легко пропустить: Option.getOrElse принимает функцию, которая вернёт запасное значение, а S.fromMaybe — само значение. Остальное соответствует почти один к одному, как показывает таблица. В Effect 3 модуль Result назывался Either, с вариантами Right и Left, поэтому в статьях и примерах, написанных до версии 4, встречается Either.

Effect<A, E, R>

В уроке «Каррирование и Асинхронность (Эволюция)» запросы были промисами, а ошибка любого шага попадала в один catch. Промис начинает работу в момент создания, и по его типу не видно, что попадёт в catch. Effect устроен иначе: это ленивое описание работы, значение, которое можно хранить, передавать и собирать из частей. Ничего не выполняется, пока описание не передадут в Effect.runPromise или Effect.runSync. У типа Effect<A, E, R> три параметра: A — тип результата, E — ошибки, которые могут случиться, R — сервисы, нужные для запуска. Если ошибок или сервисов нет, на их месте стоит never — тип без единого значения; незаписанные E и R тоже равны never, поэтому Effect<string> — это Effect<string, never, never>. Возможная ошибка видна в сигнатуре так же, как возможное отсутствие значения видно в Maybe a.

Schema: проверка данных на границе

Типы TypeScript проверяются только при компиляции, а ответ сервера приходит во время выполнения, и его они не проверят. Об этом предупреждал комментарий в примере урока «Функциональное программирование». Schema описывает данные один раз, и из этого описания получаются и тип, и проверка во время выполнения. Schema.decodeUnknownResult(схема) даёт функцию проверки, а она возвращает Result: Success с проверенными данными или Failure с описанием того, что не так.

TypeScript
import { Result, Schema } from 'effect'

// Схема описывает данные один раз: из неё получаются и тип, и проверка
const User = Schema.Struct({
  name: Schema.String,
  status: Schema.Literals(['online', 'offline']),
  age: Schema.Number,
})

// Тип выводится из схемы, interface руками писать не нужно
type User = typeof User.Type

const Users = Schema.Array(User)

// Проверка возвращает Result: Success с данными или Failure с ошибкой
const check = (data: unknown): string =>
  Result.match(Schema.decodeUnknownResult(Users)(data), {
    onSuccess: (users: ReadonlyArray<User>) => 'пользователей: ' + users.length,
    onFailure: () => 'данные не прошли проверку',
  })

// Ответы «сервера»: во втором возраст пришёл строкой
console.log(check([{ name: 'John', status: 'online', age: 25 }]))
// 'пользователей: 1'
console.log(check([{ name: 'Alex', status: 'offline', age: '18' }]))
// 'данные не прошли проверку'

Программа целиком

Осталось собрать всё в одну программу. Effect.gen читается как async/await: вместо await пишется yield*, а ошибки не уходят в общий catch, а копятся в типе. Ошибки с тегом объявляются через Data.TaggedError: поле _tag отличает одну ошибку от другой, а Effect.catchTag обрабатывает ошибку по её тегу. Option в версии 4 — не эффект, поэтому его переводят в эффект через Effect.fromOption и указывают, какой ошибкой станет None.

TypeScript
import { Array as Arr, Data, Effect, pipe, Schema } from 'effect'

const User = Schema.Struct({
  name: Schema.String,
  status: Schema.Literals(['online', 'offline']),
  age: Schema.Number,
})

// Ошибки с тегом: поле _tag отличает одну ошибку от другой
class FetchError extends Data.TaggedError('FetchError')<{
  readonly reason: string
}> {}
class UserNotFound extends Data.TaggedError('UserNotFound')<{}> {}

// «Сервер»: эффект, который может упасть с FetchError
// fetchAllUsers :: Effect<unknown, FetchError>
const fetchAllUsers = Effect.tryPromise({
  try: (): Promise<unknown> => Promise.resolve([
    { name: 'John', status: 'online', age: 25 },
    { name: 'Alex', status: 'offline', age: 18 },
    { name: 'Angel', status: 'online', age: 18 },
  ]),
  catch: (cause) => new FetchError({ reason: String(cause) }),
})

// Effect.gen читается как async/await: yield* вместо await
// program :: Effect<string, FetchError | SchemaError | UserNotFound>
const program = Effect.gen(function* () {
  const data = yield* fetchAllUsers
  const users = yield* Schema.decodeUnknownEffect(Schema.Array(User))(data)
  const first = pipe(
    users,
    Arr.filter((user) => user.status === 'online' && user.age > 20),
    Arr.head,
  )
  // Option не эффект: переводим его в эффект со своей ошибкой
  const user = yield* Effect.fromOption(first, () => new UserNotFound())
  return user.name
})

// Пока ничего не выполнено: program — только описание работы.
// Обработанные ошибки уходят из типа, в конце Effect<string, never>
const safe = program.pipe(
  Effect.catchTag('UserNotFound', () => Effect.succeed('')),
  Effect.catch(() => Effect.succeed('сервис недоступен')),
)

Effect.runPromise(safe).then(console.log) // 'John'

Тип program говорит, что программа вернёт строку или завершится одной из трёх ошибок: FetchError, SchemaError или UserNotFound. Effect.catchTag убирает из типа UserNotFound, Effect.catch обрабатывает все оставшиеся, и в конце остаётся Effect<string, never>: компилятор знает, что необработанных ошибок нет. Без обработки ошибки остались бы в типе, а Effect.runPromise при ошибке вернул бы отклонённый промис.

Третий параметр, R, в примере пуст. В настоящем коде через него проходят зависимости: база данных, HTTP-клиент, конфигурация. Сервис объявляется через Context, реализация подставляется через Layer, а Effect.runPromise принимает только эффект с R = never, поэтому забытую зависимость покажет компилятор. В тестах тот же сервис подменяется другим Layer. Кроме того, в библиотеку встроены конкурентность, повторы и тайм-ауты: Effect.all с параметром concurrency, Effect.retry и Effect.timeout. Это темы для отдельного разговора, здесь достаточно знать, что они есть.

Где Effect окупается

  • Бэкенд и интеграции с несколькими точками отказа — сеть, база данных, очереди: ошибки видны в типе, а повторы, тайм-ауты и отмена встроены в библиотеку.
  • Долгоживущий код, который правят многие люди: компилятор показывает необработанные ошибки и незакрытые зависимости.
  • Внешние данные: Schema даёт и тип, и проверку из одного описания.
  • Конкурентные задачи, где нужно ограничить число параллельных операций и уметь их отменять.
  • Тесты, в которых сервисы подменяются через Layer.

Где Effect не окупается

  • Скрипты, прототипы и простой CRUD-фронтенд: ошибка там стоит дёшево, а освоение библиотеки — дорого.
  • Команда без TypeScript, без времени на обучение или с частой сменой людей: каждому новичку придётся осваивать модель эффектов.
  • Клиентская страница, где важен каждый килобайт: размер бандла стоит измерить на своём проекте до решения.

Версии, fp-ts и что дальше

Примеры написаны для Effect 4: Effect 4.0.0 вышел 1 октября 2026 года, а ветка 3.x ещё получает исправления. Предшественник Effect в TypeScript — библиотека fp-ts. Проект fp-ts объявил о слиянии с экосистемой Effect, и по README fp-ts, Effect можно считать преемником fp-ts v2. Последний релиз fp-ts, 2.16.11, вышел 18 августа 2025 года. Для нового кода разумный выбор — Effect, а fp-ts остаётся там, где он уже используется. Версии и даты приведены по данным реестра npm на октябрь 2026 года.

Дальше — урок «Как выбрать библиотеку для ФП»: в нём Effect сравнивается с Vanilla JS, Lodash, Ramda, Sanctuary и fp-ts по бюджету, этапу проекта и команде. Документация Effect: effect.website.

Главное

  • pipe из effect принимает сначала значение, затем шаги: pipe(x, f, g). Option с вариантами Some и None соответствует Maybe, Result с Success и Failure — Either, а Option.getOrElse принимает функцию, а не значение.
  • Effect<A, E, R> — ленивое описание работы: A — результат, E — возможные ошибки, R — нужные сервисы. Ничего не выполняется до Effect.runPromise или Effect.runSync.
  • Ошибки с тегом объявляются через Data.TaggedError, Effect.catchTag обрабатывает их по тегу и убирает из типа. Effect.gen читается как async/await, только вместо await пишется yield*.
  • Schema описывает данные один раз и даёт из этого описания и тип, и проверку во время выполнения: типы TypeScript сами по себе внешние данные не проверяют.
  • Effect окупается там, где у ошибки высокая цена: бэкенд, интеграции, долгоживущий код, внешние данные. В скриптах, прототипах и простом фронтенде цена освоения обычно выше пользы.

Упражнения

Упражнение 1

Эффект — описание работы, а не сама работа. Повторите эту идею на чистом JavaScript, без библиотек, с именами как в Effect. sync(thunk) возвращает описание { run: thunk } и ничего не вызывает. map(f)(effect) возвращает новое описание: при запуске оно запустит effect и применит f к результату. runSync(effect) запускает описание и возвращает результат. Счётчик calls показывает, сколько раз «запрос» выполнился на самом деле. Сравните с промисом: что покажет счётчик сразу после new Promise?

Заготовка

let calls = 0

// fetchName :: () -> String, «запрос», который считает свои вызовы
const fetchName = () => {
  calls += 1
  return 'John'
}

// sync :: (() -> a) -> Effect a
// map :: (a -> b) -> Effect a -> Effect b
// runSync :: Effect a -> a
// ваш код

const program = map((name) => name.toUpperCase())(sync(fetchName))
console.log(`после сборки: ${calls}`)
console.log(runSync(program))
console.log(runSync(program))
console.log(`после двух запусков: ${calls}`)

new Promise((resolve) => resolve(fetchName()))
console.log(`сразу после new Promise: ${calls}`)

Ожидаемый вывод

после сборки: 0
JOHN
JOHN
после двух запусков: 2
сразу после new Promise: 3
Показать решение
let calls = 0

// fetchName :: () -> String, «запрос», который считает свои вызовы
const fetchName = () => {
  calls += 1
  return 'John'
}

// sync :: (() -> a) -> Effect a
// описание — объект с функцией run, которую пока никто не вызвал
const sync = (thunk) => ({ run: thunk })

// map :: (a -> b) -> Effect a -> Effect b
// новое описание: при запуске запустит effect и применит f, а сейчас ничего не делает
const map = (f) => (effect) => ({ run: () => f(effect.run()) })

// runSync :: Effect a -> a
// единственное место, где работа выполняется
const runSync = (effect) => effect.run()

const program = map((name) => name.toUpperCase())(sync(fetchName))
console.log(`после сборки: ${calls}`)
console.log(runSync(program))
console.log(runSync(program))
console.log(`после двух запусков: ${calls}`)

// промис начинает работу в момент создания, без всякого запуска
new Promise((resolve) => resolve(fetchName()))
console.log(`сразу после new Promise: ${calls}`)

Упражнение 2

Ошибки с тегом без библиотеки. Результат — объект { _tag: 'Success', value } или { _tag: 'Failure', error }, и у каждой ошибки тоже есть поле _tag. Напишите findOnline(id): если пользователя с таким id нет, верните Failure с ошибкой { _tag: 'UserNotFound', id }; если он не в сети — Failure с { _tag: 'UserOffline', id }; иначе Success с его именем. Затем напишите catchTag(tag, handler): функцию от результата, которая превращает Failure с ошибкой этого тега в Success со значением handler(error), а любой другой результат возвращает без изменений. Так работает Effect.catchTag: обработанная ошибка исчезает, остальные проходят дальше. Только в Effect обработчик возвращает эффект, например Effect.succeed('гость'), а здесь для простоты — само значение.

Заготовка

const succeed = (value) => ({ _tag: 'Success', value })
const fail = (error) => ({ _tag: 'Failure', error })

const users = [
  { id: 1, name: 'John', status: 'online' },
  { id: 2, name: 'Alex', status: 'offline' },
]

// show :: Result -> String, разбор по _tag результата и ошибки
const show = (result) =>
  result._tag === 'Success' ? `Success (${result.value})` : `Failure (${result.error._tag})`

// findOnline :: Number -> Result
// catchTag(tag, handler) :: Result -> Result
// ваш код

const ids = [1, 2, 3]
ids.forEach((id) => {
  const result = catchTag('UserNotFound', () => 'гость')(findOnline(id))
  console.log(`${id}: ${show(result)}`)
})

Ожидаемый вывод

1: Success (John)
2: Failure (UserOffline)
3: Success (гость)
Показать решение
const succeed = (value) => ({ _tag: 'Success', value })
const fail = (error) => ({ _tag: 'Failure', error })

const users = [
  { id: 1, name: 'John', status: 'online' },
  { id: 2, name: 'Alex', status: 'offline' },
]

// show :: Result -> String, разбор по _tag результата и ошибки
const show = (result) =>
  result._tag === 'Success' ? `Success (${result.value})` : `Failure (${result.error._tag})`

// findOnline :: Number -> Result
const findOnline = (id) => {
  const user = users.find((u) => u.id === id)
  if (user === undefined) return fail({ _tag: 'UserNotFound', id })
  if (user.status !== 'online') return fail({ _tag: 'UserOffline', id })
  return succeed(user.name)
}

// catchTag(tag, handler) :: Result -> Result
// ошибка с этим тегом становится Success, всё остальное проходит без изменений
const catchTag = (tag, handler) => (result) =>
  result._tag === 'Failure' && result.error._tag === tag ? succeed(handler(result.error)) : result

const ids = [1, 2, 3]
ids.forEach((id) => {
  const result = catchTag('UserNotFound', () => 'гость')(findOnline(id))
  console.log(`${id}: ${show(result)}`)
})

// UserOffline никто не обработал: ошибка осталась в результате,
// как в Effect она осталась бы в типе E
