## Задача

(письмо Google Search Console «Страница с переадресацией») нужно сделать правки

## Бриф

**Коротко.** Дефекта в текущем коде нет, правка кода не нужна. Оба URL из письма GSC редиректят намеренно,
а «Страница с переадресацией» — не ошибка, а нормальный статус для адреса-редиректа. Причину `/de` без слеша
устранили ещё 18.07 (8a8f65c); Google 22.07 просто перепроверил запомненный старый адрес. Предлагаю
закрыть как «не дефект». Регресс-проверка на слеши — по желанию, уровень S.

### Что просят

Владелец переслал письмо GSC от 15.10.2026: «Новые причины препятствуют индексированию — Страница
с переадресацией» и просит «сделать правки». Надо понять, что сломано, и починить, если сломано.

### Как воспроизвести (по выводу отладчика и отчёту GSC)

- GSC, sc-domain:rihard-developer.ru, «Индексирование страниц»: 2 непроиндексированных URL, причина
  «Страница с переадресацией», выявлено 07.04.2026, проверка «Не начато», просканированы 22.07.2026:
  - `http://rihard-developer.ru/` → 301 → `https://rihard-developer.ru/` (в GitHub Pages включено `https_enforced: true`);
  - `https://rihard-developer.ru/de` → 301 → `/de/` (GitHub Pages сам дописывает слеш к каталогу) →
    `/de/` — заглушка с meta-refresh и canonical на `/`.
- Проиндексировано 5 страниц. Отправлен `sitemap_index.xml`, статус «Успешно» (обработан 15.10.2026).

### Ожидаемое и фактическое

- Ожидаемое: адреса, на которые ссылается сам сайт (sitemap, canonical, hreflang, href), отдают 200 без
  редиректа. Адреса-редиректы (`http://…`, удалённая локаль `/de`) Google не индексирует, а показывает
  в разделе «Страница с переадресацией». Так и должно быть.
- Фактическое сейчас: совпадает с ожидаемым. В текущем gh-pages (8699ff7, деплой 13.09) и в исходниках
  nuxt4 нет ни ссылок на наш домен без слеша, ни `http://` (проверил `git grep` по origin/gh-pages).
  Sitemap содержит 4 адреса, все со слешем: `/`, `/course/`, `/ru/`, `/ru/course/`.
- Фактическое в июне (деплои gh-pages 3497a0c и c6ee3a5, на сайте с 05.06 по 18.07): в index.html был
  `hreflang="de" href="https://rihard-developer.ru/de"`, а в sitemap — `<loc>…/de</loc>`, оба без слеша.
  Отсюда Google и узнал про `/de`.

### Причина

- `/de`: до 8a8f65c (18.07) в конфиге не было `trailingSlash`, поэтому hreflang и sitemap генерировались
  без слеша. Сейчас исправлено: `nuxt.config.ts:44` (`site.trailingSlash: true`) и `nuxt.config.ts:73`
  (`i18n.trailingSlash: true`). Выкачено деплоем 3161e94 от 18.07. Локаль de убрана намеренно в 9030f35,
  вместо неё стоит заглушка `public/de/index.html` (то же для fr, hy, ka, kk).
- `http://`: это поведение хостинга (принудительный https в GitHub Pages), а не кода. Ссылок на `http://`
  нет ни в одном деплое.

### Известно точно

- Код ссылок строится через localePath/switchLocalePath: TheFooter.vue:44, LangSwitch.vue:45, TheHeader.vue:27,
  CourseSection.vue:23 (по выводу отладчика).
- Canonical и hreflang главной — `https://rihard-developer.ru` без слеша. Это корень, редиректа нет, не дефект.
- `robots.txt` в gh-pages указывает на `sitemap_index.xml`.
- Тестового фреймворка в проекте нет (в package.json нет `test`). Красного теста на текущем коде не будет,
  потому что дефекта нет.
- Отладчик написал проверку, на 30 строк, только встроенные модули Node:
  `/private/tmp/claude-501/-Users-rihard-projects-portfolio-nuxt3/4dc60d21-7622-4f9a-b93a-f5adf853a571/scratchpad/bin/check-slash.mjs <dir>`.
  На 3497a0c она падает (FAIL, 13 URL, код 1), на текущем origin/gh-pages проходит (OK, код 0).

### Не знаем

- Через какую команду владелец деплоит: `npm run deploy` (predeploy сработает сам) или `npm run deploy:app`.
  Это важно только для того, куда встраивать проверку.
- Как sitemap заведён в Яндекс.Вебмастере: `/sitemap.xml` или `/sitemap_index.xml`. Это важно только
  для `/sitemap.xml`, см. «Вне рамок».

### Где в коде

- Фикс, который уже есть: `nuxt.config.ts:37-45` (site), `nuxt.config.ts:70-73` (i18n).
- Заглушки удалённых локалей: `public/{de,fr,hy,ka,kk}/index.html`, комментарий `nuxt.config.ts:57-60`.
- Если делаем регресс-проверку: новый `scripts/check-slash.mjs`. Образец — `scripts/deploy.mjs`:
  шебанг, ESM, встроенные модули, путь к выводу через `new URL('../.output/public', import.meta.url)`, строка 10.

### Критерии готовности

Вариант A, «закрыть как не дефект» (рекомендую):
1. Код, конфиги и `public/` не меняются.
2. На origin/gh-pages нет ссылок на наш домен без слеша (кроме корня) и нет `http://rihard-developer.ru`
   в `.html` и `.xml`. Уже выполнено.
3. В GSC владелец не нажимает «Проверить исправление»: оба URL продолжат редиректить, и проверка «не пройдёт».
   Оба URL останутся в разделе «Страница с переадресацией» — это нормальное конечное состояние.

Вариант B, «A + регресс-проверка» (по решению владельца):
1. `scripts/check-slash.mjs`: Node ESM, шебанг, `chmod +x`, только `node:` модули. Каталог необязательным
   аргументом, по умолчанию `.output/public` (как в deploy.mjs:10).
2. После `nuxt generate` на nuxt4 печатает `OK` и выходит с кодом 0.
3. На дереве июньского деплоя 3497a0c печатает FAIL, выходит с кодом 1 и перечисляет адреса без слеша,
   включая `/de`.
4. Ссылка `http://rihard-developer.ru/...` — FAIL, код 1.
5. Пропускает без ошибки: корень `https://rihard-developer.ru`, адреса с расширением файла (`.png`, `.xml`),
   пути `/_nuxt/`, `/__sitemap__/`, meta-refresh заглушек и чужие домены.
6. Каталог не существует или в нём нет ни одного `.html`: понятное сообщение и код 1, а не ложный `OK`.
   Пустой вывод generate не должен проходить проверку.
7. Место запуска — по ответу на вопрос 2. `npm run lint` и `npm run typecheck` проходят, если работают в проекте.

### Вне рамок

- Удалять заглушки `public/{de,fr,hy,ka,kk}/` ради 404. Это хуже: Google потеряет сигнал редиректа
  на `/` для уже известных адресов.
- Отключать принудительный https в GitHub Pages.
- `/sitemap.xml` → 301 → `/sitemap.xml/` (в gh-pages это каталог `sitemap.xml/index.html` с meta-refresh
  на `/sitemap_index.xml`, его генерирует prerender модуля sitemap, так во всех деплоях с июня). Сейчас на него
  никто не ссылается: ни код, ни robots.txt, ни GSC. На индексацию не влияет. Рекомендую не трогать.
  Если адрес когда-нибудь попадёт в тот же отчёт GSC, это опять норма, а не ошибка.
- Миграция `scripts/deploy.sh` → `scripts/deploy.mjs` (незакоммиченная работа владельца) — не наша задача.

### Зависимости

- В рабочем дереве nuxt4 есть незакоммиченные правки владельца: `package.json` (deploy → deploy.mjs),
  `scripts/deploy.mjs` (новый файл), `AboutSection.vue`, `ru.json`. Вариант B затрагивает либо `package.json`,
  либо `deploy.mjs`, поэтому начинать его стоит после того, как владелец закоммитит эти правки.
- Других задач, миграций и внешних систем нет. GSC и GitHub Pages не меняем.

### Цена ошибки

- Вариант A: ничего не ломается. Риск в том, что будущая регрессия (кто-то уберёт `trailingSlash` или добавит
  ссылку без слеша) всплывёт только через недели, очередным письмом GSC. Цена — цепочки редиректов
  и лишний расход краулингового бюджета, а не потеря страниц.
- Ложная «починка»: удалить заглушки или трогать редиректы — значит превратить известные Google адреса в 404
  или в дубли. Это хуже, чем сейчас.
- Вариант B с блокировкой деплоя: при ложном срабатывании деплой встанет, пока не поправят проверку.

### Вопросы

1. Как закрываем задачу?
   - A: «не дефект», без правок кода (рекомендую);
   - B: A + регресс-проверка `scripts/check-slash.mjs`.

   Почему спрашиваем: в письме просят «правки», а чинить нечего. Проверка — единственная осмысленная
   работа здесь, но это защита на будущее, а не исправление.
2. Если B — где она запускается?
   - B1: в начале `scripts/deploy.mjs`, перед push. Блокирует любой деплой — и `npm run deploy`,
     и `deploy:app`. `package.json` не меняется.
   - B2: только вручную, одной строкой в package.json `"check:urls": "node scripts/check-slash.mjs"`.
     Деплой не блокирует.

   Почему спрашиваем: B1 ловит регрессию автоматически, но правит ваш ещё не закоммиченный deploy.mjs
   и может остановить деплой. B2 безопаснее, но полагается на память.
3. `/sitemap.xml`: в Яндекс.Вебмастере sitemap заведён как `/sitemap.xml` или как `/sitemap_index.xml`?
   Почему спрашиваем: если как `/sitemap.xml`, Яндекс получает HTML-редирект вместо XML. Тогда нужна
   отдельная задача. Если как `sitemap_index.xml` или не заведён — оставляем как есть.

### Решения владельца

> «По задаче 1 пункты 1. не дефект 2. Да 3. да.»

1. Причина в GSC — не дефект; при этом регресс-проверка нужна (вариант B, ответ «Да» на вопрос 2).
2. Место запуска — B1: первым шагом в `scripts/deploy.mjs` (ответ владельца: «В deploy.mjs»). `package.json` не меняется.
   Правки владельца (deploy.sh → deploy.mjs и др.) закоммичены в nuxt4: d122d50, 18e3787, 055dc07.
3. `/sitemap.xml` — «да»: нужна отдельная задача, `/sitemap.xml` не должен отдавать HTML-редирект. Вынесено в задачу №3.
